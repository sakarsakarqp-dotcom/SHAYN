# تأسيس الحساب الموحد وعضويات المؤسسات — شَيْن

الحالة: مسودة تنفيذية على فرع `feat/identity-organization-foundation`، وليست مدمجة في `main`.

## ما أضيف

- `migrations/007_identity_organizations.sql`: إضافة جداول أدوار الحساب الشخصي المتعددة، المؤسسات، عضويات الفرق، الدعوات، وسجل تدقيق المؤسسة.
- `prisma/schema.prisma`: خريطة Prisma أولية للجداول الحالية والجداول الجديدة ضمن مخطط PostgreSQL `shayn`.

## قرارات تصميمية

1. يظل `users.role` مخصصا لأدوار الإشراف العامة الحالية (`user/admin/moderator/super_admin`). لا نخلط صلاحيات إدارة المنصة مع صفات الحساب المهنية.
2. تُحفظ صفات المستخدم المهنية في `user_roles`، ويسمح الحساب الواحد بأكثر من صفة: باحث عن عمل، صاحب عمل، مستقل، مقدم خدمة، بائع، مشتري.
3. تُدار صلاحيات الشركات والفرق من خلال `organizations` و`organization_memberships`، ولا تمنح عضوية مؤسسة تلقائيا صلاحيات على مؤسسة أخرى.
4. تحفظ الدعوات بصيغة تجزئة الرمز فقط في `token_hash`، ولا يخزن رمز الدعوة الخام.
5. أضيف سجل تدقيق لعمليات المؤسسة.
6. لا يجري ترحيل استنتاجي للأدوار القديمة؛ لا يمكن استنتاج ما إذا كان صاحب إعلان قد أراد صفة بائع أو صاحب عمل أو مستقل من نوع الإعلان وحده.

## ما لم يُنفذ بعد

- لم تُشغّل الترحيلة على PostgreSQL فعلية.
- لم تُضف واجهات API لإدارة الأدوار أو المؤسسات أو الدعوات.
- لم تُربط Prisma runtime بالخادم ولم تُضف حزمة Prisma إلى مسار التشغيل.
- ملف Prisma خريطة أولية ويجب التحقق منه باستخدام إصدار Prisma المعتمد قبل استخدامه لتوليد عميل أو ترحيلات.
- إنشاء المؤسسة يجب أن يضيف عضوية المالك في معاملة واحدة؛ يجب تطبيق هذا في طبقة الخدمة قبل إتاحة endpoint الإنشاء.

## طريقة المراجعة

راجع الترحيلة قبل تشغيلها على أي قاعدة بيانات، وخذ نسخة احتياطية. لا تشغّلها تلقائيا عند إقلاع التطبيق. بعد اعتماد إصدار Prisma، نفّذ فحص schema ومقارنة introspection مع قاعدة اختبار، ثم ضع سياسة واضحة لإدارة تاريخ الترحيلات قبل نقل التحكم إلى Prisma Migrate.
