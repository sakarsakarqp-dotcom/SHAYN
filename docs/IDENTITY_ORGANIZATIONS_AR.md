# الحسابات متعددة الأدوار وواجهات المؤسسات — شَيْن

الحالة: تنفيذ مرحلي على الفرع `feat/identity-organization-api-v2`؛ لم يُدمج في `main` ولم يُنشر على Render.

## ما هو موجود في هذا الفرع

- `migrations/007_identity_organizations.sql`: جداول الصفات المهنية المتعددة، المؤسسات، العضويات، الدعوات، وسجل التدقيق.
- `prisma/schema.prisma`: خريطة Prisma أولية للجداول ضمن مخطط PostgreSQL `shayn`.
- `server.js`: واجهات API للأدوار المهنية والمؤسسات والدعوات وسجل التدقيق.
- `scripts/apply-identity-migration.js`: مشغّل صريح للترحيل رقم 007.
- `tests/organization-api.test.js`: اختبار تكامل HTTP لتدفقات الحساب والعضوية وحدود الصلاحيات.

## واجهات API المضافة

| الطريقة | المسار | الغرض |
|---|---|---|
| GET | `/api/me/roles` | قراءة صفات الحساب المهنية |
| PUT | `/api/me/roles` | استبدال صفات الحساب المهنية المسموح بها |
| GET | `/api/organizations` | عرض المؤسسات التي للمستخدم عضوية فعالة فيها |
| POST | `/api/organizations` | إنشاء مؤسسة وإضافة مالكها في معاملة واحدة |
| GET | `/api/organizations/:id` | قراءة مؤسسة لعضو فعّال |
| GET | `/api/organizations/:id/members` | عرض الأعضاء للمالك أو المدير |
| POST | `/api/organizations/:id/invitations` | إنشاء دعوة لعضوية |
| POST | `/api/organizations/invitations/accept` | قبول دعوة للمستخدم صاحب البريد المطابق |
| GET | `/api/organizations/:id/audit` | قراءة سجل التدقيق للمالك أو المدير |

## حدود الصلاحيات

1. `users.role` يظل مخصصاً لصلاحيات المنصة العامة مثل user/admin/moderator/super_admin.
2. `user_roles` للصفات المهنية فقط: job_seeker/employer/freelancer/service_provider/seller/buyer. اختيار صفة مهنية لا يمنح صلاحية إدارة المنصة.
3. عضوية المؤسسة مستقلة ومحددة بالمؤسسة؛ العضوية في مؤسسة لا تمنح وصولاً إلى مؤسسة أخرى.
4. إنشاء الشركة أو الجهة يتطلب صفة employer؛ المتجر يتطلب seller؛ الفريق يتطلب freelancer أو service_provider.
5. إنشاء المؤسسة وإضافة عضوية owner وسجل التدقيق يتم داخل معاملة PostgreSQL واحدة.
6. الدعوة تحفظ تجزئة SHA-256 للرمز فقط، وتنتهي بعد سبعة أيام، ولا تقبل إلا عند تسجيل الدخول بالبريد المدعو.
7. رمز الدعوة الخام يعاد مرة واحدة إلى مدير المؤسسة؛ إرسال البريد غير مفعّل بعد، لذلك يكون التسليم يدوياً عبر قناة آمنة.

## ترحيل قاعدة البيانات

الترحيل 007 لا يعمل تلقائياً عند إقلاع التطبيق. هذا مقصود لتجنب تغيير قاعدة الإنتاج بصمت.

بعد أخذ نسخة احتياطية ومراجعة قاعدة SHAYN، نفّذ من بيئة تشغيل موثوقة:

```bash
npm run db:migrate:identity
```

ثم أعد تشغيل الخدمة. إذا لم تكن الجداول الخمسة موجودة، تعيد واجهات وحدة الهوية حالة HTTP 503 بدلاً من الفشل بخطأ قاعدة بيانات غير واضح.

## التحقق والقيود

- اختبار GitHub Actions في PR #4 تحقق من الترحيل والعلاقات وصحة مخطط Prisma على PostgreSQL مؤقتة.
- نجح اختبار HTTP في PR #5 على PostgreSQL 16 مؤقتة بتاريخ 27 نوفمبر 2026؛ شمل تسجيل حسابين، الصفات المهنية، إنشاء مؤسسة، دعوة وقبولها، منع العضو العادي من الدعوة، ومنع الصفة المهنية من منح صلاحية إدارة المنصة. [نتيجة CI](https://github.com/sakarsakarqp-dotcom/SHAYN/actions/runs/45964502710).
- Prisma Client غير مدمج في وقت التشغيل بعد؛ الخادم الحالي يستخدم `pg`، ومخطط Prisma مرجع متحقق منه فقط.
- لا يوجد إرسال بريد للدعوات، أو اعتماد/توثيق للمؤسسات، أو إدارة تغيير الأعضاء وإلغاء الدعوات من الواجهة بعد.
- لا توجد واجهات React/TypeScript لهذه الوظائف حتى الآن.
- لا يوجد اتصال بقاعدة إنتاج أو تحقق حي من Render ضمن هذا التغيير.
