# شَيْن | SHAYN — خط الأساس التنفيذي للمنتج
> الإصدار: 0.1 — مسودة تنفيذية على فرع `feat/unified-platform-foundation`
> الحالة: غير معتمد نهائياً؛ يوثق ما هو موجود وما يجب بناؤه.

## 1. الاتجاه الثابت
- الانطلاق من سوريا مع تصميم يسمح بالتوسع إلى أسواق عربية.
- منظومة واحدة تضم: SHAYN Jobs، SHAYN Projects، SHAYN Services، SHAYN Market، SHAYN Trust.
- حساب شخصي واحد يمكنه حمل أدوار متعددة، مع عضويات منفصلة للشركات والمؤسسات.
- تجهيز المنظومة ككل، ثم إطلاق القدرات تدريجياً. لا يعني الإطلاق التدريجي حذف أي قسم من الرؤية النهائية.

## 2. الواقع التقني الذي تم التحقق منه
المستودع الأساسي المشار إليه في README هو `sakarsakarqp-dotcom/SHAYN`. ويطلب README عدم تطوير النسخة المكررة `shayn-syria`.
- التطبيق الحالي Node.js 20 + Express + PostgreSQL.
- الواجهة الحالية تخدم من `public/index.html` و`public/app.js` و`public/style.css`.
- توجد مصادقة بالبريد وكلمة المرور، إعلانات عامة لأنواع job/project/service/market/business، تقديم ورسائل وتقييمات وبلاغات وإدارة.
- يوجد مسار طلبات شراء أولي للمنتجات، والسيرفر يصرّح بأن الدفع الإلكتروني غير مفعل.
- قاعدة البيانات تستخدم مخطط PostgreSQL منفصلاً باسم `shayn` حسب README وتهيئة الخادم.
- متغيرات التشغيل موثقة في `.env.example`، ولا يجوز حفظ أسرار حقيقية في المستودع.
- فحص `npm run check` يفحص صياغة ملف الخادم وملف الواجهة الحالي.

## 3. الفجوات بين الموجود والرؤية
1. دور المستخدم في المخطط الحالي مفرد، وليس نظام أدوار متعددة.
2. لا يوجد نموذج مكتمل لعضويات الشركات ودعوات الفريق وصلاحيات كل مؤسسة.
3. Jobs وProjects وServices ما زالت ممثلة إلى حد كبير بنموذج إعلان مشترك، وتحتاج دورات حياة خاصة.
4. Market لديه سلة وطلبات أولية، لكن لا يوجد دفع إلكتروني أو تسوية أو مخزون متكامل؛ لا نعدّ ذلك متاحاً.
5. Trust يحتوي على بلاغات وتقييمات أولية، لكنه لا يحقق توثيق الهوية أو الشركات أو إدارة نزاعات متكاملة.
6. لا يجوز وصف أي قسم بأنه مكتمل قبل وجود اختبارات وظيفية وأمنية موثقة.

## 4. المتطلبات الوظيفية العليا

### 4.1 الحساب والهوية
- تسجيل ودخول واستعادة وصول آمنة.
- ملف شخصي أساسي واحد.
- تفعيل أدوار متعددة دون إنشاء حسابات مكررة.
- ملفات مهنية مستقلة عند الحاجة: باحث عن عمل، مستقل، مقدم خدمة، بائع.
- فصل حساب المؤسسة عن حساب الشخص، وربط الأعضاء بعضويات ذات صلاحيات.
- إبطال جلسات وصلاحيات العضوية فور الإيقاف.

### 4.2 SHAYN Jobs
- نشر وظيفة مع المسمى والوصف والتصنيف والموقع ونمط العمل ونوع الدوام ومتطلبات الخبرة.
- استقبال طلبات التقديم وسير ذاتية/ملفات اختيارية.
- حالات الطلب: جديد، قيد المراجعة، قائمة مختصرة، مقابلة، مقبول، مرفوض، منسحب.
- صاحب العمل يرى طلبات وظائف مؤسسته فقط؛ والمتقدم يرى طلباته فقط.

### 4.3 SHAYN Projects
- نشر موجز مشروع ومتطلبات ومهارات وميزانية/عملة اختيارية وموعد.
- استقبال عروض المستقلين ومقارنتها واختيار عرض.
- مراحل وتسليمات وتعليقات وملفات وسجل قبول/طلب تعديل.
- لا توجد محفظة أو ضمان مالي أو دفع مرحلي قبل التحقق القانوني ومزود الدفع.

### 4.4 SHAYN Services
- إنشاء صفحة خدمة تشمل وصفاً ونطاق العمل ومدة تقديرية وحزم اختيارية.
- طلب خدمة مع تفاصيل ومتطلبات ومرفقات.
- حالات الطلب: بانتظار الرد، مقبول، قيد التنفيذ، بانتظار التسليم، تعديل مطلوب، مكتمل، ملغى.
- فصل الخدمة المنشورة عن الطلب الناتج عنها.

### 4.5 SHAYN Market
- متاجر وبائعون ومنتجات وصور وأسعار وعملة وحالة توفر.
- سلة وطلبات مع لقطة ثابتة لاسم المنتج وسعره عند الطلب.
- إدارة حالة الطلب ومعلومات التوصيل بحماية البيانات الشخصية.
- الدفع الإلكتروني والمخزون المتقدم والتسويات مؤجلة حتى التحقق من المتطلبات.

### 4.6 SHAYN Trust
- بلاغات على حساب أو إعلان أو تعامل.
- توثيق حساب/شركة كعملية مراجعة بموافقة واضحة وبيانات محمية.
- تقييمات مرتبطة بتفاعل أو معاملة مؤهلة، لا تقييمات مفتوحة بلا سياق.
- ملف نزاع، أطراف، أدلة، حالة، قرار، وسجل إجراءات.
- لا يُعرض وصف "موثّق" قبل إتمام مراجعة فعلية وفق سياسة منشورة.

### 4.7 الإدارة
- إدارة المستخدمين والأدوار والمؤسسات والتصنيفات والإعلانات والبلاغات.
- سجل تدقيق للقرارات الحساسة.
- صلاحيات الإدارة محددة حسب الدور، مع حماية حساب المدير الأعلى.

## 5. قواعد غير وظيفية وأمنية
- التحقق من التفويض في الخادم لكل طلب، وليس إخفاء عناصر الواجهة فقط.
- عزل بيانات المؤسسات على مستوى الاستعلامات والملكية.
- أقل صلاحية لازمة، ورفض افتراضي عند غياب الإذن.
- تشفير النقل عبر HTTPS/TLS، وعدم تسجيل كلمات المرور أو الرموز أو بيانات حساسة.
- حدود حجم الملفات والطلبات، وفحص نوع الملف قبل قبوله.
- نسخ احتياطية مجدولة واختبار استعادة موثق.
- سجل تدقيق للعمليات الإدارية والمالية والحساسة.
- واجهة عربية RTL متجاوبة، مع بنية ترجمة وتعدد عملات/بلدان قابلة للتوسع دون تثبيت أسعار صرف.

## 6. ترتيب التنفيذ
1. تدقيق التطبيق الحالي وإصلاح الأعطال الأمنية/الوظيفية الحرجة.
2. تصميم الحساب الموحد والأدوار وعضويات المؤسسات.
3. فصل نماذج البيانات ودورات العمل للأقسام الخمسة.
4. بناء Trust والإدارة وسجل التدقيق بالتوازي مع العمليات الأساسية.
5. استكمال دليل التصنيفات وخريطة UX/UI.
6. توثيق API وقاعدة البيانات والاختبارات.
7. تجهيز بيئة تجريبية ثم إطلاق مغلق.
8. مراجعة الدفع والمتطلبات المحلية قبل تفعيل أي تدفق مالي.

## 7. معايير عدم الادعاء بالاكتمال
لا يُعلن عن ميزة بأنها جاهزة إلا إذا:
- نُفذت في المستودع الأساسي.
- اتصلت بقاعدة بيانات فعلية.
- اختُبرت بحسابات وأدوار مختلفة.
- اختُبر منع الوصول غير المصرح به.
- وثقت طريقة تشغيلها وحدودها.
- لم تعتمد على أسرار أو إعدادات غير موجودة في بيئة النشر.

## 8. قرارات مفتوحة
- مزود الاستضافة وقاعدة البيانات النهائيان.
- طريقة التسجيل والتحقق (بريد/هاتف/كليهما).
- البلدان والعملات الأولى بعد سوريا.
- مزودو الدفع والتوصيل وما يسمح به قانونياً.
- سياسة التوثيق والاحتفاظ بالوثائق والنزاعات.
- رسوم الاشتراك أو العمولات أو أي نموذج إيرادات.
- سياسة المنتجات المحظورة وآلية الإشراف.
